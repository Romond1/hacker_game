# Phase 2.1 Mission and Training Framework Design

## Objective

Build additive, reusable campaign-mission and skill-training frameworks without changing the behavior of working Phase 1 systems. Phase 2.1 will prove the training framework with a player-visible **Systems Calibration** module unlocked after Mission 3. Mission 4 and its copy/paste mechanic remain out of scope until this framework is complete and tested.

## Protected Baseline

Phase 1 is preserved in Git commit `ac1956e` and annotated tag `phase-1-complete`. Both are pushed to `https://github.com/Romond1/hacker_game.git`. The Phase 2.1 work starts on `codex/phase-2.1-training-framework`.

The implementation must remain additive and retain all existing behavior for Missions 1–3, authentication, progression, XP, Credits, shop, inventory, equipment, identity, achievements, replay, teacher reset, and teacher dashboards.

## Chosen Approach

Use separate, typed mission and training frameworks that share the existing progression, reward, achievement, visual-effect, and persistence infrastructure.

The existing source-controlled mission definitions remain the campaign content catalog. A reusable mission shell will coordinate common lifecycle and completion behavior, while mission-specific mechanics and validation remain adapters. Existing Missions 1–3 will use compatibility adapters so their content and interaction behavior do not need to be rewritten.

Training will have its own catalog and session engine because a repeatable skill exercise is not a campaign mission. Each module supplies configuration and a focused skill adapter; the shared engine owns session flow, timing, scoring, statistics, persistence, rewards, results, and replay.

This approach avoids both a risky universal-activity refactor and unnecessary server-authored content management.

## Mission Framework

### Mission definition

Extend the existing mission definition with typed metadata for:

- rank and prerequisite requirements;
- XP and Credit policy references;
- associated training module;
- replay behavior;
- unlocks, achievements, and story flags;
- completion text and optional theme, warning, timer, and bonus settings;
- a mission-mechanic adapter responsible for active interaction and validation.

### Mission lifecycle

`MissionTemplate` will own the standard states:

1. locked;
2. available;
3. briefing;
4. active;
5. validating/saving;
6. completion presentation;
7. replay or return.

The shell will expose narrow callbacks and state to the active mechanic. A mechanic cannot award its own rewards or mutate progression directly.

### Completion presentation

A reusable completion presentation will use the current ACCESS GRANTED language, confetti, sound, reward counters, progression display, and button styling. It will show canonical XP, Credits, achievements, rank or unlock changes, and mission-specific completion text. Continue controls become available within approximately three seconds, and reduced-motion mode will shorten motion while retaining every result.

## Training Framework

### Training module definition

A source-controlled training catalog will register typed definitions containing:

- stable training ID, title, description, linked skill, and linked mission;
- unlock requirement and supported difficulty configuration;
- configurable round count;
- task generator version and seeded task generator;
- validation and scoring rules;
- time rules and mistake penalties;
- XP policy, Credit reward per completed run, and lifetime module Credit cap;
- achievement triggers;
- a skill adapter that renders and validates one task.

The generic interfaces will support operations such as text copy/paste, file copy/move/rename, search, typing, mouse control, browser tabs, transfer, and keyboard shortcuts without encoding any one of those mechanics into the session engine.

### Session lifecycle

`TrainingSession` will own:

1. intro;
2. server-issued attempt start;
3. generated round;
4. round validation and result capture;
5. advance through the configured number of rounds;
6. completion submission;
7. trusted results presentation;
8. replay or return.

It will aggregate current round, total rounds, elapsed time, score, successful validations, errors, accuracy, streak, and per-round evidence. The skill adapter owns only task generation inputs, task interaction UI, and validation output.

### Systems Calibration proof module

Systems Calibration is a real player-visible module unlocked after Mission 3 and may be retired or superseded when Mission 4 adds the first curriculum-specific training module. It proves the complete framework through five randomized code-matching rounds.

Initial policy:

- five rounds per run;
- up to 150 XP per completed run according to score;
- one Credit per completed run;
- 20-Credit lifetime module cap;
- continued play, XP, records, ranks, and achievements after the Credit cap;
- seeded generation so the backend can reproduce and validate the task set.

## Components and Data Flow

### Frontend components

- `MissionTemplate`: mission lifecycle and common presentation.
- `TrainingCenter`: catalog-driven module grid and unlock status.
- `TrainingSession`: session state machine, timer, round aggregation, save/retry, and replay.
- `TrainingTaskAdapter`: pluggable generation, rendering, and validation contract.
- `TrainingResults`: reusable 3–5 second result and reward presentation.
- Pure training domain functions: accuracy, score, rank, streak, personal-best comparison, and seeded generation helpers.

### Runtime flow

1. Home Base receives persisted training summaries with player progression.
2. Mission 3 completion makes Systems Calibration available through its catalog unlock rule.
3. The player enters the Training Center and starts the module.
4. The server creates an attempt with the registered module ID, difficulty, generator version, and random seed.
5. The browser deterministically generates the five tasks and records round evidence.
6. On completion, the browser submits the attempt ID and evidence, never trusted reward amounts or caps.
7. The backend reproduces and validates the registered tasks, calculates canonical results and rewards, updates persistence, and returns the result receipt.
8. The result screen renders only server-returned reward and progression data.

## Persistence Model

A new additive migration will introduce immutable training attempts and per-player/module progress.

Training attempts store the player, module, difficulty, generator version, seed, timestamps, aggregate statistics, evidence, completion state, and reward event ID. The design must allow a future table or policy dimension for rank, campaign-section, or milestone reward pools without changing attempt identity.

Per-player/module progress stores:

- total completed runs;
- rewarded runs;
- Credits earned from the module;
- highest score;
- fastest qualifying completion;
- best accuracy;
- longest streak;
- highest completion rank;
- last completion time.

Unlock status is derived from trusted mission/progression state and catalog requirements rather than a client-controlled flag. All relevant records persist through refresh, logout, login, and browser restart in both the local development backend and production MySQL implementation.

## Authoritative Completion Transaction

Training completion will execute as one database transaction:

1. authenticate the student and load the server-issued attempt;
2. lock player and module-progress rows;
3. return the original receipt for an already completed attempt;
4. validate the registered module, generator version, seed, and submitted round evidence;
5. calculate authoritative score, accuracy, time, completion rank, and XP;
6. calculate at most the next available one-Credit reward under the 20-Credit module cap;
7. call the existing reward-ledger service with a stable training source/event ID;
8. update only personal-best fields improved by this result;
9. grant achievements through the existing achievement pipeline;
10. persist completion and return the canonical result, reward receipt, Credit-cap totals, achievements, and updated progression.

The client cannot choose XP, Credits, caps, unlocks, or achievements. Concurrent and repeated submissions cannot duplicate rewards.

## Credit Cap and Anti-Farming Behavior

Credits are awarded once per successfully completed run, never per round. The Training Center, active-session context, and result screen will show the module allowance as `earned / cap`.

At `20 / 20`, the UI will state **TRAINING REWARD COMPLETE** and explain that the player may continue for XP, scores, achievements, ranks, and personal records. The backend reward policy enforces the cap even when the client is modified or multiple completion requests race.

The reward interfaces will accept optional future pool dimensions for module, rank, campaign section, and milestone. Phase 2.1 implements only the module cap.

## Personal Bests and Achievements

Personal-best updates compare each dimension independently. A slower high-score run can improve score without overwriting fastest time; a fast inaccurate run cannot overwrite best accuracy. Completion-rank comparison uses an explicit ordered rank scale.

Phase 2.1 integrates these achievement triggers with the existing pipeline:

- **FIRST TRAINING**: complete any training module;
- **PERFECT CALIBRATION**: complete Systems Calibration with 100% accuracy;
- **SPEED OPERATOR**: finish under the module-configured threshold;
- **TRAINING MASTER**: earn all 20 available Credits from Systems Calibration.

Achievement checks remain data-driven and idempotent.

## Training Center and Visual Design

The Training Center becomes accessible from Home Base after the first module is unlocked. It renders a catalog-driven grid with module status, linked skill, difficulty, completion count, personal best, and visible Credit-cap meter. Future locked modules can be registered without creating new page structures.

The active session will show round progress, elapsed time, running score, successes, errors, accuracy, and streak. It will reuse the existing dark interface, orange accent, typography, panels, profile styling, button language, confetti, sounds, and reduced-motion conventions.

The reusable results presentation will show:

- TRAINING COMPLETE;
- score, time, accuracy, rank, and personal-best changes;
- XP and Credits earned;
- module Credits earned and cap;
- achievements;
- replay and return actions.

## Error Handling

- A completion network error preserves the completed result and evidence on-screen and offers retry.
- Duplicate retries return the original canonical receipt.
- An invalid, expired, unknown, or stale attempt displays a recoverable message and returns the player to the Training Center.
- Saving and retry states block accidental repeated interaction and are accessible to keyboard and screen-reader users.
- The timer uses monotonic elapsed-time calculation while the session is active and submits bounded integer seconds.
- Unsupported generator versions fail closed without awarding rewards.

## Teacher Dashboard

The existing teacher list remains unchanged. The individual student record gains one compact training summary containing associated skill, completed runs, best score, best accuracy, and Credits earned. Detailed per-round evidence remains in persistence and tests but does not clutter the teacher UI.

## Verification Strategy

### Pure domain tests

- score, time, accuracy, rank, streak, and penalties;
- independent personal-best comparisons;
- seeded task reproducibility and variation;
- reward-cap boundaries and post-cap play;
- mission and training unlock requirements.

### Component tests

- mission lifecycle compatibility for Missions 1–3;
- Training Center locked, unlocked, partial-cap, and completed-cap states;
- intro, five configurable rounds, validation, timer, results, replay, and return;
- visible XP/Credit results and cap messaging;
- save failure and idempotent retry;
- keyboard interaction and reduced motion.

### Backend tests

- authenticated attempt creation and completion;
- unlock enforcement;
- server-side evidence and policy validation;
- idempotency, tamper rejection, Credit cap, achievements, and persistence;
- concurrent completion cannot double-award;
- local development backend and PHP/MySQL contract parity.

### Regression and browser verification

Retain coverage for Missions 1–3, shop, inventory, equipment, profile, reward sequence, teacher reset, and dashboards. Add a browser journey covering Mission 3 unlock, Training Center entry, five rounds, result/reward display, replay, Credit-cap visibility, and persistence after refresh and login.

Before Phase 2.1 is declared complete, run the full test suite, TypeScript check, production build, server-contract checks, available PHP checks, and browser journey. Then commit and push Phase 2.1 separately and create the annotated tag `phase-2.1-training-framework`.

## Out of Scope

- Mission 4 story or skill-specific implementation;
- copy/paste training;
- Missions 5–6;
- multiple fully implemented difficulty modes;
- rank, campaign-section, or milestone-wide Credit pools;
- teacher content authoring;
- broad refactors of Phase 1 systems.

## Definition of Done

Phase 2.1 is complete when the reusable mission and training contracts, lifecycles, persistence, trusted scoring/rewards, caps, unlocks, results, achievements, teacher summary, and player-visible Systems Calibration module work together; all relevant state survives a new session; Phase 1 regressions are absent; and the verified Phase 2.1 commit and tag are pushed to GitHub.
