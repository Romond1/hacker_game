# Phase 2.3 Game Feel Design

## Status and constraints

Phase 2.2 is protected by the pushed `phase-2.2-complete` tag. Phase 2.3 keeps all mission, training, economy, persistence, inventory, and teacher-dashboard contracts intact. It adds presentation and interaction feedback only; server responses remain authoritative for rewards and purchases.

The visual thesis is **reactive terminal**: the existing dark hacker interface gains sharp 120–800 ms responses, sparse signal motion, compact operator interventions, and deliberately paced reward reveals. Motion remains functional and restrained. No new animation dependency, canvas system, media, currency, mission, or database migration is needed.

## Chosen approach

Use lightweight React state machines plus CSS transforms, opacity, gradients, and the existing synthesized WebAudio system. This is preferable to adding a motion library because the required effects are short and finite, and preferable to canvas because the interface must remain readable and inexpensive on student laptops.

Use reusable pieces only where they recur:

- `AmbientLayer`: decorative grid, scan, and signal variants; always hidden from assistive technology.
- `ProgressMeter`: labeled, numeric, accessible progress for campaign, training credits, and affordability.
- `OperatorMessage`: short contextual message with replaceable operator mark and polite live-region behavior.
- `RewardCounter`: delayed count-up with a static reduced-motion result.
- `StoryBeatSequence`: configurable steps with text, tone, sound, duration, and optional skip.
- `PurchaseReveal`: processing, acquired, and action stages around the existing authoritative purchase call.
- extended sound manager: semantic sound names mapped through one replaceable theme and centrally throttled.

Ordinary buttons and cards will use shared CSS interaction states rather than being mechanically wrapped in new components.

## Screen behavior

### Home Base and Profile

Home Base gets one ambient grid/scan layer, active-node emphasis, explicit `NEW SIGNAL`, stable secured and locked states, and contextual campaign progress. The profile becomes an identity panel with codename and rank dominance, current XP/credits, campaign progress, and visible equipped avatar, badge, and theme slots. State remains textually explicit and never depends on color or animation.

### Mission briefings and play

The reusable briefing presents mission number and story command first, a short objective next, then localized mission objectives as numbered visual task steps. Longer briefing text becomes secondary intel. Mission controls retain their exact behavior while gaining focus, press, validation, success, and failure feedback. A small operator message appears only for useful state changes.

### Mission completion

The existing saved completion result feeds a presentation-only sequence:

1. `VALIDATING...` for a brief interval.
2. success impact and mission-complete sound.
3. XP count-up.
4. Credit count-up.
5. compact progression/unlock reveals.
6. explicit `CLAIM REWARDS` or `CONTINUE` action.

The reward is already saved before this sequence, so closing or skipping the presentation cannot duplicate or lose it. Reduced motion collapses the sequence to final readable values without count-up movement.

### Training Center and results

Training modules become arcade-style selectable cards with best score, status, and the existing credit-cap progress. Completion briefly analyzes performance, then stages score, XP, credit, rank, and personal-best results. Replay and return behaviors remain unchanged.

### Hacker Shop

Cards retain the current catalog and purchase/equip APIs while gaining stronger rarity, ownership, equipped, lock, preview, and affordability states. Locked items remain visible with requirements. An affordability meter states current credits, cost, and remaining credits. Purchase uses a sub-two-second processing state followed by an item-acquired reveal with `EQUIP NOW` and `RETURN TO SHOP`; the reveal follows the server result and cannot grant items itself.

### Story and operator systems

One configurable UI sequence will drive at least two existing transitions: the incoming-transmission story beat and a reward/unlock transition. The operator is a lightweight CSS/SVG-like terminal mark rather than a fixed character asset so it can be replaced later. Messages stay brief, contextual, and non-blocking.

## Sound, motion, and accessibility

The current WebAudio synthesizer remains the only audio engine. Add semantic hover, click, panel, validation, XP, credit, purchase, and equip categories to a default theme map. Hover and count sounds are throttled centrally. Audio is created only after user interaction, reads the existing persistent mute preference, and exposes no per-component audio implementation.

`prefers-reduced-motion` disables ambient travel, shimmer, glitch, and count-up motion while preserving final state and focus feedback. Hover effects have press/tap equivalents. Overlays use bounded scrolling on small screens. Focus-visible outlines, ARIA progress semantics, live regions, labels, icons, and text retain accessible state communication.

## Verification

Tests will cover reusable primitives and state sequences, mission selection/briefing/completion/counters/claim, training analysis and personal best, shop lock/affordability/purchase/equip, sound mute persistence and throttling, story/operator rendering, and reduced-motion-safe final states. The existing full frontend, server-contract, PHP policy/security/economy, and browser journey suites must remain green. Desktop and narrow screenshots will be inspected for key screens before tagging and pushing `phase-2.3-game-feel`.
